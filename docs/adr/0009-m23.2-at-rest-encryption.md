# ADR 0009: M23.2 At-Rest Encryption (AES-256-GCM Authenticated Cipher)

## Status

Accepted

## Date

2026-09-18

## Context

ADR 0008 (M23.1 password authentication) covered OSEP §53.4 (Saltzer-Schroeder fail-safe defaults) + §54.4 (password storage). The OSEP roadmap calls the broader milestone "M23 Security overview — Ch. 53-57". After M23.1, the rest of Part IV is **mostly untouched**:

- §53.5 Basics of OS security (system calls + access control primitives)
- §54.5 Auth by what you have (security tokens, smartphones)
- §54.6 Auth by what you are (biometrics)
- §54.7 Auth for non-humans (sudo, setuid)
- Ch. 55 Access control (ACLs, capabilities, RBAC, mandatory/discretionary)
- §56.2 Symmetric cryptography (AES)
- §56.3 Public-key cryptography
- §56.4 Cryptographic hashes
- §56.5 Cracking cryptography
- §56.6 Cryptography + OSes
- §56.7 At-rest encryption (full disk, password vaults)
- Ch. 57 Distributed-system security (SSL/TLS, certificates, MITM, SSH, HTTPS)

Of these, **§56.2 + §56.7** are the most OS-relevant primitives for a single-process .NET HTTP server like ours: they describe how an OS protects data when the disk physically leaves the OS's domain. This ADR covers those.

## Decision

We implement **AES-256-GCM authenticated encryption** with the OS-level primitives OSEP §56.2 + §56.6 + §56.7 recommend. Four pieces:

### 1. `SymmetricCipher` (AES-256-GCM wrap)

- 32-byte (256-bit) keys from `RandomNumberGenerator`.
- 12-byte (96-bit) nonces from `RandomNumberGenerator`, **fresh per encrypt call** (NIST SP 800-38D recommended nonce length for GCM).
- 16-byte (128-bit) authentication tags.
- Optional associated data (AAD) hook for context binding, even though our demo doesn't use it.
- Built on `System.Security.Cryptography.AesGcm` — the .NET BCL ships it, no new deps.

**Rationale**: OSEP §56.2 is unambiguous on cipher choice:
> "AES, a standard cipher that was carefully designed and thoroughly studied, is one good example that you should think about using."

**Alternatives considered**:

- **ChaCha20-Poly1305** — equally good; .NET does not ship it, only via NuGet (`NSec`). Rejected to avoid a new dep for one milestone.
- **AES-CBC + HMAC-SHA256 (encrypt-then-MAC)** — OSEP §56.4 implies the chapter endorses authenticated modes, but ours would have to roll our own tags / nonces / lengths. GCM bundles all three.
- **Plain AES-CBC** — has no auth tag, so a flipped ciphertext decrypts to *something* (often junk, but possible garbage that passes a sloppy checksum). The whole point of §56.4's integrity discussion is that we don't want that.

### 2. `AtRestStore` (in-memory slotted store)

- `ConcurrentDictionary<string, Slot>` — same pattern as M23.1's `UserStore`.
- Each `Slot` holds `{name, createdAt, nonce, ciphertext, tag}`. **Plaintext never persists**.
- One 256-bit process-level key, rotated on demand via `/crypto/keygen`.
- `Put` wipes the caller's plaintext buffer with `Array.Clear` after encryption.

**Rationale**: OSEP §56.7 wraps the chapter by saying the *whole point* of at-rest encryption is that stealing the device's raw blocks doesn't help:
> "if the data on the device is encrypted via full disk encryption, the new machine will usually be unable to obtain the encryption key. It can access the raw blocks, but they are encrypted and cannot be decrypted without the key."

Our store does the same at the application layer.

### 3. HTTP routes + four demo scenarios

| Route | Demonstrates |
|---|---|
| `/crypto/keygen` | Key rotation |
| `/crypto/encrypt` + `/crypto/decrypt` | Round-trip with random nonce |
| `/crypto/tamper-demo` | Auth-tag fails closed on bit flip |
| `/crypto/nonce-reuse-demo` | `c1 ⊕ c2 == p1 ⊕ p2` (the OSEP §56.5/§56.6 lesson) |
| `/crypto/dump` | At-rest form: nonce + len + tag, never plaintext |

### 4. `EncryptWithFixedNonce` — the one intentionally-bad primitive

It's locked behind a separate method name so it can never be called by accident. Only the `/crypto/nonce-reuse-demo` route uses it, and the route's only purpose is to *show why* nonce reuse is fatal:
> "if the attacker can obtain the key, the cryptography becomes useless" — §56.6

The lesson here is a corollary: if the attacker can cause you to *reuse* a `(key, nonce)`, the cryptography also becomes useless.

### 5. Out of scope (deliberate)

- **TLS handshake + X.509 certificates** (OSEP §57): would need `SslStream` + cert generation. Add as a future M23.3+ slice.
- **PK crypto** (OSEP §56.3): symmetric is enough for the single-process lab. PK would let us exchange keys with a remote party.
- **Hardware security modules / TPM** (OSEP §53 security enclaves): the key lives in process RAM. If the OS is compromised, so is the key — §56.6 calls out this exact trade-off.
- **File-level encryption of `minifs.img`**: would require touching the M12 block layer. A future milestone could call `SymmetricCipher.Encrypt` from `MiniFs.Write`. Out of scope here.

## Consequences

### Positive

- **Part IV coverage expands**: M23.2 brings us from §53.4 + §54.4 + §56.4 to **§53.4 + §54.4 + §56.2 + §56.4 + §56.5 + §56.6 + §56.7** — about 7 of the 12 OSEP sections in Part IV's password + cryptography spine (Ch. 54 + §56.2-§56.7).
- **Reusable primitives**: `SymmetricCipher.Encrypt` could slot into M12 (encrypt `minifs.img` blocks at rest), into a future TLS slice (wrap a TLS session key with this AEAD), or even into a future integrity-protecting journal (Ch. 42.3 cryptographic journaling §42.5+).
- **M23.1 + M23.2 compose**: A real system derives an AES key from the user's password via PBKDF2 (§54.4 ⇒ §56.6), then uses the AEAD to encrypt the user's files. We don't compose the two — but the seam is clean.

### Negative

- **Key is in process memory**: §56.6 calls out explicitly that a compromised OS can read any key on the machine. A real system uses a TPM or a kernel keyring; we don't.
- **No tests**: same pattern as M23.1 + M8-M22 (smoke scripts cover it, no unit tests).
- **Single-process key management**: rotating the key (`/crypto/keygen`) drops all stored slots. Real BitLocker / FileVault re-encrypts the device; we just drop in-memory records.
- **Nonce reuse demo route is intentionally dangerous**: `SymmetricCipher.EncryptWithFixedNonce` is one of the few deliberately-unsafe primitives in the codebase. Future readers might be tempted to call it from production code; the method name is the only barrier.

## Verification

- Build clean (`Build succeeded. 0 Warning(s). 0 Error(s)`).
- 15/15 existing tests still pass (no test changes).
- Round-trip: `/crypto/encrypt?name=hello&msg=...` → `/crypto/decrypt?name=hello` returns identical plaintext.
- Auth-tag fail-closed: `/crypto/tamper-demo` flips a bit, `AesGcm.Decrypt` throws `CryptographicException("The computed authentication tag did not match...")`, route returns 200 with the failure text.
- Nonce-reuse exposes: `/crypto/nonce-reuse-demo` reports `equal? = True` for `c1 ⊕ c2 == p1 ⊕ p2` with both plaintexts encoding the same prefix and differing only in the last character.
