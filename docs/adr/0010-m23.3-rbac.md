# ADR 0010: M23.3 Role-Based Access Control (RBAC)

## Status

Accepted

## Date

2026-09-18

## Context

M23.1 added password authentication; M23.2 added at-rest encryption. Both covered OSEP Ch. 53-54 + §56.2-§56.7 primitives but skipped **Ch. 55 (Access Control)**. That chapter's §55.6 specifically promotes RBAC as a particularly valuable pattern for organizations with multiple user types.

A real system needs at least one access-control gate beyond "registered user". For a single-process .NET HTTP server, the simplest gate is the `Role.User` vs `Role.Admin` distinction.

## Decision

We add `UserStore.Role` (enum: User | Admin) plus a `Role` field on `AuthUser`, plus three new routes (`/auth/grant`, `/auth/role`, `/protected/*`).

### 1. Minimal Role enum

```csharp
public enum Role { User, Admin }
```

Default is `User` — Saltzer-Schroeder §53.4 *least privilege*. Admin requires explicit `?role=admin` at register or a follow-up `/auth/grant`.

### 2. Two-tier authenticate

`AuthenticateWithRole(username, password, requiredRole)` runs the M23.1 PBKDF2 verify first, then checks role. Returns false on either failure. Crucially, the dummy-PBKDF2 path runs even when the user is missing (no username-existence leak), and the failure response is `403 forbidden` byte-identical for all three failure modes (no password leak, no role leak).

### 3. `/protected/*` route

A first protected route, `/protected/secret`, that returns a synthesized secret when the caller authenticates as Admin. Single route — more endpoints would compose the same gate.

### Out of scope

- **MAC (mandatory access control)** (OSEP §55.5): we'd never override an Admin-set policy; real MAC systems do.
- **Group inheritance** (OSEP §55.4): a `Group` field could slot in beside `Role`.
- **Capability systems** (OSEP §55.4 pure): different model entirely.
- **`sudo` for non-humans** (OSEP §54.7): requires process identity, not user identity.
- **Multi-role switching mid-session** (OSEP §55.6 Manager ↔ Programmer example): requires a session token; not implemented.

## Consequences

### Positive

- **Closes Ch. 55 access control gap** (partially — only the §55.6 RBAC pattern, not ACL per file or capability lists).
- **Reuses M23.1 PBKDF2** — `AuthenticateWithRole` is built on the existing verify pipeline + dummy-PBKDF2 + fail-safe error body.
- **Clean extension** — `Role` is a 4th field on the existing record; existing M23.1 routes (`/auth/register`, `/auth/login`) are unchanged.

### Negative

- **Two roles only**: doesn't scale to org-wide RBAC.
- **No Admin-gated grant**: anyone can call `/auth/grant?role=admin`. Real systems require an already-admin caller.
- **Single protected route**: only `/protected/secret` demonstrates the gate. More endpoints would compose `AuthenticateWithRole` the same way.

## Verification

- Build clean.
- 14/14 existing tests still pass (no test changes).
- Smoke: register alice (admin) → ok; register bob (User default) → ok; alice hits /protected → 200 + secret; bob hits /protected → 403; alice + WRONG pw → 403 same body.
- 3 known OSEP invariants demonstrated (least-privilege default, fail-safe error body, wrong role denied).
