# ADR 0011: M23.4 Public-Key Cryptography (RSA-2048 Sign + Verify)

## Status

Accepted

## Date

2026-09-18

## Context

M23.1–M23.3 covered password authentication, at-rest encryption, RBAC. The OSEP Part IV Security coverage §56.3 (public-key cryptography) was uncovered.

PK is what the chapter calls out as the *better* mechanism for "authenticate an entity to many parties" (web site to many users), as opposed to passwords which work best for "many parties authenticate to one" (each user to the web site).

A real PK slice needs to demonstrate: keypair generation, sign with private, verify with public, distribution of the public key via some "I got your public key from somewhere trustworthy" mechanism (X.509 in real systems; OSEP §57.3).

## Decision

We add `MiniCrypto.RsaSigner` with three operations: `Generate`, `Sign`, `Verify` (with optional externally-supplied public key). `System.Security.Cryptography.RSA.Create(2048)` for the keypair. `SignData` + `VerifyData` with SHA-256 + PSS for the signatures. Public keys distributed as SPKI/DER hex bytes.

### 1. RSA-2048, SHA-256, PSS

OSEP §56.5 / §57.5 both endorse "RSA with 2048 bit keys". PSS is the recommended modern padding; PKCS#1 v1.5 signatures remain widespread but PSS has stronger security proofs.

### 2. In-memory private key, public byte-pipe

The private key never leaves process memory. The public key is exported and may be distributed in any way (here: hex SPKI over HTTP). This mirrors §56.6's "bet entirely on secrecy of the key" with the practical lab constraint that we don't have a TPM.

### 3. Externally-distributed public keys via `/crypto/import-pubkey`

A real system uses X.509 certs (OSEP §57.3). We skip the CA chain but model "I got your public key from somewhere" by accepting `?pubkey=` on `/crypto/verify`. This is enough to demonstrate *cross-process* verification.

### Out of scope

- **Asymmetric encryption** (RSA-OAEP).
- **Hybrid encryption** (PK encrypt + symmetric encrypt — the OSEP §56.3 "Alice does both" example).
- **X.509 certificate chains** (OSEP §57.3).
- **HSM / TPM-backed keys**: in-process RSA only.
- **Key revocation lists** (OSEP §57.6).

## Consequences

### Positive

- **Closes §56.3**: the public-key primitive is now demonstrated end-to-end in this lab.
- **Composes with M23.5 handshake**: a follow-up could replace our symmetric-IKM with ECDH + sign with PK for proper mutual auth (OSEP §57.3).
- **Symmetric fingerprint**: a `Verify` failure is byte-stable (always "FAIL" body) so an attacker can't tell from the response what went wrong.

### Negative

- **Single signer**: only one in-memory keypair. A multi-tenant system would need a key registry.
- **No certificate chain**: trust requires external X.509 infrastructure we don't build.
- **2048-bit key**: smoke-time RSA keygen takes ~50-100 ms (Microsoft's CSP), so the `/crypto/rsa-keygen` route is the slowest route in the lab. Real systems use larger keys (4096) for batch flows + smaller keys for hot paths.

## Verification

- Build clean.
- 14/14 existing tests still pass (no test changes).
- Smoke: `rsa-keygen` → `sign` → `verify(msg=hello)` → OK; `verify(msg=goodbye)` → FAIL.
- Same signature hex used across OK and FAIL; the verification rejects based on the message body.
