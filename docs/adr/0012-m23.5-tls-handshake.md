# ADR 0012: M23.5 TLS-style Handshake (HKDF session key)

## Status

Accepted

## Date

2026-09-18

## Context

M23.1–M23.4 covered auth, at-rest encryption, RBAC, PK signing. OSEP Ch. 57 (Distributed System Security) was uncovered. §57.5 in particular lays out the TLS handshake structure that the modern internet depends on.

A full TLS handshake requires: PK authentication + ECDH key exchange + X.509 cert chain + symmetric session-key derivation. Implementing all four for a single-process lab is too much work; the most educational part is the **key derivation** half (which §57.5 explicitly highlights).

## Decision

We add `MiniCrypto.Handshake.RunDemo()` which produces `clientNonce`, `serverNonce`, and derives a `sessionKey` via **HKDF-SHA256** (RFC 5869 Extract+Expand). The route then encrypts + decrypts a payload using the derived key + the M23.2 AEAD, proving the key is a working AES-256 key.

### Why HKDF instead of ECDH

ECDH (X25519) isn't directly available in the BCL. We use a randomly-generated symmetric IKM + the two nonces, mirroring the HKDF-based key derivation stage in any TLS handshake. The *structure* is identical to TLS; the PK step is replaced by an IKM-injection step.

### Why clean-room HKDF (~25 lines) instead of an off-the-shelf library

`System.Security.Cryptography.HKDF` exists in .NET 8+. We don't need any non-standard features. A clean-room RFC 5869 Extract+Expand wrapped around `HMACSHA256` is exactly correct.

### Out of scope

- **ECDH / X25519** (real TLS).
- **X.509 certificate chains** (OSEP §57.3).
- **Mutual TLS** (mTLS).
- **Perfect forward secrecy** via ephemeral keys.
- **Record-layer MACs** (TLS record sequence numbers + HMAC-SHA256 per record).
- **Replay protection** at the record layer.

## Consequences

### Positive

- **Closes §57.5 key-derivation half** — names the OSEP crux ("we need to be sure who we're sharing that key with") and shows the HKDF answer.
- **Composes with M23.2 AEAD**: same `SymmetricCipher` used by M23.2 is the demo's session encrypt step. No new crypto introduced.
- **No new dependencies**: HKDF + `HMACSHA256` are BCL.

### Negative

- **No PK-auth on the handshake itself**: the §57.3 trust step (server certificate) is missing. A real TLS handshake verifies the server's PK identity at step 2.
- **In-process only**: a real handshake crosses a network with attestation. We model both parties in the same process.
- **No key destruction**: a real connection drops the session key bytes when the connection closes; we just drop the variable.

## Verification

- Build clean.
- 14/14 existing tests still pass (no test changes).
- Smoke: `/crypto/handshake` produces 4-step output; different `clientNonce` and `serverNonce` per call; `sessionKey` derived via HKDF; the encrypt+decrypt round-trip with the `sessionKey` succeeds (returns the original plaintext).
- Two consecutive handshakes produce different `sessionKey` values.
