# ADR 0013: M23.6 TOTP — Auth by What You Have (RFC 6238)

## Status

Accepted

## Date

2026-09-18

## Context

M23.1 (password) + M23.3 (RBAC) + M23.4 (PK) cover most of OSEP Ch. 54 authentication. The chapter's §54.5 "Authentication by What You Have" was uncovered — except for a brief mention in M23.1's overview.

The most realistic "what-you-have" mechanism for a single-process lab is **TOTP** (RFC 6238): the canonical algorithm implemented by Google Authenticator, Authy, 1Password, and every smartphone authenticator app.

## Decision

We add `MiniCrypto.Totp` with `Compute` + `Verify` + `ToBase32`. RFC 6238 dynamic truncation. HMAC-SHA256 instead of HMAC-SHA1 (RFC 6238 §1.2 allows either; SHA-256 is the modern default). 30-second step + 6-digit truncation. ±1 step verification window.

### 1. RFC 6238 dynamic truncation

```
offset = hmac[31] & 0x0f         // last byte low 4 bits
binary = ((hmac[offset] & 0x7f) << 24) | ...    // 4 bytes, high bit masked
code   = binary % 1_000_000       // 6 digits
```

### 2. HMAC-SHA256, not HMAC-SHA1

SHA-1 remains in the RFC default but is on the cryptographic-deprecation list (§56.4). SHA-256 is what real services use today. Same key derivation pattern either way.

### 3. ±1 step window

30-second step + 1-step skew window = the standard authentication-app tolerance for clock-drift. Tight window reduces the brute-force surface; loose window accommodates cheap-clocks.

### 4. No server-side replay protection

A real TOTP service remembers which (code, step) pairs have already been accepted. We accept the same code within the same window any number of times. Documented as future work.

### 5. Composition with M23.1 password (deferred)

Adding `?totp=CODE` to `/auth/login` is a one-line change but requires careful semantics (which secret is paired with which user?). Deferred.

## Consequences

### Positive

- **Closes §54.5** — the "what-you-have" primitive is demonstrated end-to-end (compute, verify, base32 enrollment).
- **No new dependencies** — `HMACSHA256` is BCL.
- **Composes with M23.1**: a future `/auth/login?user=X&pass=Y&totp=N` would be a single-line addition to the existing auth block.

### Negative

- **No replay tracking**: an attacker who captured a code within the window could replay it.
- **No rate-limiting**: combined with the no-replay-tracking gap, an attacker could brute-force 1M codes per 30s window per username.
- **No enrollment flow**: secrets are supplied via URL query in the demo. Real systems use QR-code enrollment.

## Verification

- Build clean.
- 14/14 existing tests still pass (no test changes).
- Smoke: `/crypto/totp-demo?msg=HEXSECRET` reports code + 4 verification results (`True`, `True`, `False`, `False` — current / ±1 step / ±2 step / wrong).
- A 32-byte random secret from `RandomNumberGenerator` is the recommended enrollment path.
