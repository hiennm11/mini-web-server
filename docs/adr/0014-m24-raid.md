# ADR 0014: M24 RAID — Redundant Arrays of Inexpensive Disks

## Status

Accepted

## Date

2026-09-21

## Context

Part III Persistence has M11 (raw I/O), M12 (vsfs + journaling), and M21 (FFS placement) on the books. OSEP Ch. 38 — the canonical chapter on RAID — is the only persistence-side chapter not yet covered by a milestone. Without RAID, the lab can't show how a filesystem survives a disk failure; without surviving a failure, the lab's persistence story is missing the "and the disk dies" half.

## Decision

We add `MiniScheduler.Raid` with four RAID levels + a parity-recovery demo.

### 1. RAID 0 / 1 / 4 / 5 — the four canonical levels

OSEP walks through six levels. The four that matter in practice and that show the **striping → redundancy → bottleneck → fix** progression are:

- **RAID 0** (§38.3): block-level striping, no redundancy. Pure performance; `N` disks = `N`× bandwidth, `N`× failure rate.
- **RAID 1** (§38.4): full mirroring on `2` disks. Doubles write cost, tolerates one disk loss, can parallelize reads.
- **RAID 4** (§38.7): block-level striping + dedicated parity disk. Cheap redundancy, but every write hits the parity disk → write bottleneck.
- **RAID 5** (§38.8): block-level striping + rotating parity. No bottleneck — parity writes spread across disks.

§38.5 (RAID 2 bit-level Hamming) and §38.6 (RAID 3 byte-level striping + parity) are omitted — both are superseded by block-level striping in practice. §38.9 (RAID 6 dual parity) is omitted — extends RAID 5's XOR to a second parity code (Reed-Solomon territory).

### 2. In-memory disks, no device-driver integration

Each "disk" is a `byte[][]` slot in process RAM. The simulator demonstrates the *layout* and *recovery* properties of RAID, not device-level latency. Real RAID lives below the filesystem; for the lab we model the layout decisions.

### 3. XOR recovery

After a disk failure, the lost block at stripe `s` on failed disk `f` is `⊕` of the surviving `N−1` blocks in the stripe. This is OSEP §38.7's "fundamental insight" — applied uniformly to RAID 4, RAID 5, and (trivially) RAID 1 (the surviving mirror has the same data).

### 4. Rotating parity is the textbook pattern

OSEP §38.8 figure 38.8 places parity for stripe `s` on disk `(s + 1) % N` for the `N`-disk array (left-to-right diagonal). We follow that diagram exactly so the `/raid/run?level=5` output matches the textbook trace.

### 5. Route exposes failure scenario

`/raid/run?level=N&disks=N&blocks=M&failed=K` runs a fixed scenario: write `M` stripes with deterministic content, optionally fail disk `K`, then read back every stripe. The output shows the layout + the recovered block (or the unrecoverable error for RAID 0).

## Consequences

### Positive

- **Closes Ch. 38** — the canonical RAID chapter is now demonstrated end-to-end.
- **Reuses M11's interface concept** — the lab already established that a filesystem sees a flat block array; RAID sits below that abstraction and is mostly invisible.
- **Composes with M12 + M21** — RAID sits below them in the stack; the lab's persistence story now has "disk dies, we recover" as the last missing piece.
- **No new dependencies** — XOR is `System.Numerics.Vector<byte>.Xor` or simple `for` loop.

### Negative

- **In-memory disks only** — no real I/O latency, no real failure timing. A future slice could model MTTF via `Random.Shared`.
- **One failure at a time** — multi-disk failure is RAID 6 territory; not modeled.
- **No chunked striping** — stripe unit = one block; chunked striping with stripe size > 1 block is a real-world optimization not demonstrated.
- **No reconstruction scheduling** — recovery is synchronous in the test; real systems rebuild in the background with throttling.

## Verification

- Build clean.
- Existing tests still pass (no test changes).
- New tests cover: RAID 0/1/4/5 round-trip read, RAID 1 mirror survives one disk loss, RAID 4/5 parity recovers the lost block, RAID 0 fails after one disk loss (no redundancy).
- Smoke: `/raid/run?level=5&disks=4&blocks=4` reproduces OSEP §38.8 figure 38.8's rotating-parity layout.
- Smoke: `/raid/run?level=5&disks=4&blocks=4&failed=2` shows the lost block recovered via XOR.
