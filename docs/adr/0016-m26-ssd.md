# ADR 0016: M26 SSD — Flash Translation Layer + Garbage Collection + Wear Leveling (OSEP Ch. 44)

## Status

Accepted

## Date

2026-09-21

## Context

Part III Persistence has M11 (raw I/O), M12 (vsfs + journaling), M21 (FFS), M24 (RAID), M25 (LFS). The persistence thread still misses the modern device layer: how a flash SSD hides the block-erase constraint and the wear-out problem from the filesystem. Without it, the lab can't show why SSDs need an FTL at all, what garbage collection actually does, or why TRIM matters.

## Decision

We add `MiniScheduler.Ssd` with the full flash model + log-structured FTL + GC + wear tracking.

### 1. Raw flash model with explicit page states

OSEP §44.3 spells out the state machine: `INVALID → ERASED → VALID`. We add `DEAD` as a fourth state (logical: the page's data is no longer pointed to by the mapping table, so GC may reclaim it). Each block is `PagesPerBlock` pages, each page is one byte (so the XOR-style smoke traces stay compact).

### 2. Page-level mapping table (not block-level, not hybrid)

OSEP §44.9 explains why page-level mapping is impractical for 1 TB devices (1 GB of mapping memory). For the simulator, page-level is the most explicit — every `Write(lba)` finds a free page and updates `mapping[lba] = physicalPage`. Real SSDs use block-level or hybrid (page-level for log blocks + block-level for data blocks) to reduce memory. We follow the textbook's primary example (§44.7) which uses page-level mapping for clarity.

### 3. GC = "block with most dead pages, migrate live, erase"

OSEP §44.8 spells out the GC protocol. We implement exactly that — pick the block with the highest dead-page count, read the live pages to the log (next free pages in the current write block), and erase the block. No switch-merge / partial-merge / full-merge distinction (those are hybrid-FTL concerns, OSEP §44.9).

### 4. Wear tracking without active wear leveling

OSEP §44.10 describes active wear leveling: periodically move cold data so that every block wears evenly. We track erase count per block (a histogram) but don't move data — the log-structured design + GC already does most of the work for free (every free page in the log block sees roughly equal write traffic).

### 5. Trim hint as a first-class operation

OSEP §44.12 calls out TRIM as a "new storage API" that emerged because of log-structured FTLs. We expose `Trim(lba)` so the route can demonstrate it: dropping the mapping entry marks the underlying page dead without rewriting it.

### 6. Route exposes three scenarios

`/ssd/run?scenario=write|gc|wear`:

- `write` — write a deterministic pattern of LBAs; observe the mapping table + block state grid + erase counts.
- `gc` — write + rewrite some LBAs to introduce dead pages, then run GC. Observe the compaction + block erase.
- `wear` — run a heavy rewrite loop, then dump the wear histogram.

## Consequences

### Positive

- **Closes Ch. 44** — the canonical SSD chapter is demonstrated end-to-end.
- **Closes the loop with M25**: LFS is a log-structured *filesystem*; SSD FTL is a log-structured *device driver*. Showing both side-by-side makes the indirection lesson concrete.
- **No new dependencies** — `Dictionary<int, int>` + arrays.

### Negative

- **Page-level mapping is impractical** for real devices; the simulator inherits OSEP §44.9's caveat.
- **No active wear leveling** — we track erase count but don't migrate cold data.
- **No over-provisioning** — the SSD reports its full capacity; real SSDs reserve 7–28% for GC.
- **No timing** — every operation is O(1); we don't model the read/program/erase latency differences.

## Verification

- Build clean.
- Existing tests still pass (no test changes).
- New tests cover: write/read round-trip via mapping table; rewrite creates dead pages; GC migrates live pages + erases a block; trim marks a page dead without rewriting; erase count increments.
- Smoke: `/ssd/run?scenario=write` shows the mapping table + block state grid.
- Smoke: `/ssd/run?scenario=gc` shows GC migration + the erased block.
- Smoke: `/ssd/run?scenario=wear` shows the erase count histogram.
